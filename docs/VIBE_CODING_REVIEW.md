# 这次 Vibe coding 的复盘

这份复盘依据本项目聊天中的实际改动。这里的「错误」指提高返工或验证成本的做法，不评价提出要求的人。反复反馈让最终方向更清楚；需要改进的是把这些反馈转成稳定、可验收的约定。

| 这次的做法 | 造成的问题 | 下一次怎样更省力 |
|---|---|---|
| 登录、同步还未验证就很快转入大量视觉迭代 | 后续同时遇到闪退、WebView 打不开、课程读不到，难判断是哪一层失败 | 先跑通一个真实账号的登录→完整课表→缓存→重新打开，再扩大功能 |
| 多次改变网格、日期底板、配色算法、菜单、背景范围、提醒规则 | 同一位置反复重写，旧需求可能残留；「字体统一」曾被实现成页内统一 | 每轮明确「替换哪条、保留哪条」，用最终基线和截图定义跨页面行为 |
| 最初把小节固定为 1–6，后来按官网实际数量显示 | 学校的小节与课程块未先定义，可能压缩或截断晚课 | 先确认数据含义：小节、连堂、周次、单双周、考试时间；用边界课表验收 |
| 使用「获取全部内容」「所有功能直接到达」这样很宽的要求 | 官网有私有接口、业务表单和状态差异，无法凭门户截图保证全部内容离线可读 | 列出目录清单、必须采集的模块、只打开官网的模块和验证范围；将读取与办理分开 |
| 一开始要求无法更新就告诉用户「教务系统崩溃了」 | 离线、登录过期、证书、WebView 或解析失败都可能被误归因 | 要求明确失败分类、最近成功时间和保留缓存，以实际证据描述故障 |
| 希望「最简单的 agent 看报告就能解决」 | 报告不能替代真实复现，有些系统进程终止甚至没有 Java 堆栈 | 报告提供版本、源码、步骤、阶段与脱敏证据；允许 AI 索要缺失的最小信息 |
| 在小米实机和 App 内真实账号同步未验收前决定标为正式版 | 版本号容易被误读为实机兼容和全部同步都已通过 | 版本名称可以先确定，但发布说明必须保留验证边界；上线前用目标手机走完整闭环 |

## 我这边同样需要承担的部分

代理应主动维护最终需求，不应让用户反复指出旧入口、演示数据或配色残留。上次「统一字体」只做到每页内部统一，没有覆盖三份背景之间的一致性，是实现范围理解不充分；本版改为三页整体取色并增加跨页检查。底栏顺序变化必须用页面身份导航，不能继续用固定第几个按钮推断功能。

浏览器里的用户登录与 App WebView 会话是两个环境；核对官网入口和前端协议，不等于手机真实全量同步成功。合成测试、模拟器冷启动、签名校验也各有边界。代理应在交付中说清这些区别，不能用一个 PASS 概括所有功能。

## 下次可直接采用的节奏

1. 先定目标手机、数据来源和三条最重要的使用路径。
2. 保存一份最终需求，每次修改只写差异和验收例子。
3. 先交一个完整闭环，再按小批次增加界面、通知和后台功能。
4. 每轮用真实截图确认视觉，用合成测试覆盖可重复规则，用真实手机/账号补齐环境差异。
5. 发布前核对 APK、源码版本、文档、权限、验证边界和回退办法；不删除可恢复的 Git 提交历史。
